# Arquitectura, ejecución, verificación y factibilidad de Skynet

## ¿La arquitectura proporciona un agente coherente para trabajar en el PC?

### Takeaway
La base reutiliza componentes adecuados y contiene defensas útiles, pero hoy hay varios contratos de trabajo que producen experiencias diferentes con la misma conversación: chat con herramientas del PC, Coder, tareas largas y Hermes. No hace falta sustituir todo para corregir el fallo; hace falta definir un contrato único de contexto, herramientas y cierre, y hacer que cada motor lo cumpla.

### Cited Findings
- El objetivo declarado es un agente personal con Core pequeño, MCP para herramientas, SQLite, git y LiteLLM. Son piezas razonables y extensibles: permisos, auditoría, almacenamiento, transporte de herramientas y bucle están separados. [README](C:/Git/Skynet/README.md:1), [Runtime](C:/Git/Skynet/skynet/runtime.py:1), [Decisiones D1–D4](C:/Git/Skynet/docs/DECISIONES.md:25).
- Seleccionar repo no equivale a asociarlo a una tarea: `active_repo` devuelve `None` si Coder está apagado; `new_task` usa ese valor para `task.repo` y distingue `chat` de `skynet`. Esto es una decisión explícita D17, también cubierta por un test que exige repo seleccionado pero tarea sin repo. [Coordinator](C:/Git/Skynet/skynet/coordinator.py:93), [test de conversación](C:/Git/Skynet/tests/test_local_listo.py:194), [D17](C:/Git/Skynet/docs/DECISIONES.md:232).
- El chat sin Coder aún puede tener `sistema` con permisos altos y herramientas internas `crear_proyecto`, `tarea_larga`, memoria y skills. Por tanto el modo aparentemente conversacional puede crear y programar un proyecto mediante rutas absolutas. La validación automática de Coordinator exige `repo` en la tarea, de modo que esas escrituras no reciben el mismo contrato de cierre que Coder. [Runtime](C:/Git/Skynet/skynet/runtime.py:162), [Coordinator verificación](C:/Git/Skynet/skynet/coordinator.py:209), [internas](C:/Git/Skynet/skynet/internas.py:117).
- `crear_proyecto` crea carpeta, git, README, pytest.ini y un test `assert True`; añade el repo a configuración y devuelve texto, pero no cambia el `task.repo` ni convierte la ejecución corriente en Coder. [crear_proyecto](C:/Git/Skynet/skynet/internas.py:61).
- La conversación adjunta creó `ecosistema-simulador` y luego utilizó `sistema.write_file`/`edit_file`/`run_command`; no es el camino normal `workspace` de Coder. Es consistente con la posibilidad anterior, aunque sin consultar la base de datos de esa ejecución no afirmo exactamente qué interruptores estaban activos. [Conversación](C:/Users/HACHO/.codex/attachments/5ea744bd-ef0d-493c-94b8-111c447a244e/Texto%20pegado.txt).
- Hermes usa su prompt, herramientas, memoria y permisos; Runtime no aplica el gate de Skynet. Su contenedor ve carpeta de usuario y `C:/Git` con algunas carpetas ocultas. Si Coder o tarea larga están activos, el router sustituye el perfil agente Hermes por local. Son decisiones explícitas, pero el selector de cerebro no significa lo mismo para todas las tareas. [Runtime](C:/Git/Skynet/skynet/runtime.py:138), [Router](C:/Git/Skynet/skynet/router.py:126), [D19](C:/Git/Skynet/docs/DECISIONES.md:258), [configuración Hermes](C:/Git/Skynet/config/skynet.toml:83).
- Pi ya tiene implementación local sin commit: `PiAgent`, puente RPC, `/coder pi`, selector API y tests. Mantiene gate/MCP de Skynet y desactiva herramientas/contexto/skills nativos de Pi; usa UUID de tarea para sesión Pi. `PROGRESO` aún dice estudio sin implementación. Conviene distinguir documentos antiguos de estado real del working tree. [PiAgent](C:/Git/Skynet/skynet_tools/pi_agent.py:81), [Runtime](C:/Git/Skynet/skynet/runtime.py:187), [Coordinator](C:/Git/Skynet/skynet/coordinator.py:361), [tests](C:/Git/Skynet/tests/test_pi.py:1), [PROGRESO](C:/Git/Skynet/PROGRESO.md:5).
- MCP se abre y cierra por cada `agent_step`, y las conexiones arrancan secuencialmente. `initialize`/`list_tools` no tienen aquí una envoltura explícita de timeout; la biblioteca puede tener límites propios, que esta auditoría no cuantifica. Esto añade trabajo por bloque y dificulta diagnósticos que esperan a todos los servidores. [Runtime](C:/Git/Skynet/skynet/runtime.py:198), [ToolHub](C:/Git/Skynet/skynet/toolhub.py:69), [doctor](C:/Git/Skynet/skynet/cli.py:204).
- Dos herramientas que parecen equivalentes ejecutan shells diferentes: `sistema.run_command` invoca PowerShell en Windows, `workspace.run_command` usa `subprocess.run(..., shell=True)`, cuyo shell predeterminado Windows es cmd; el GUIDE de Pi exige comandos PowerShell para workspace. No se ha ejecutado una demostración de error, pero el contrato escrito es inconsistente. [sistema](C:/Git/Skynet/skynet_tools/sistema.py:116), [workspace](C:/Git/Skynet/skynet_tools/workspace.py:187), [Pi GUIDE](C:/Git/Skynet/skynet_tools/pi_agent.py:18).

### Inferences
- P0: separar identidad de sesión/proyecto de estrategia de ejecución. El proyecto seleccionado debe entrar siempre con nombre, raíz, tarea activa y reglas mínimas. Coder podría cambiar cuánto contexto/herramientas/verificación se ofrece, sin borrar la identidad del proyecto.
- Crear proyecto debe devolver un identificador estructurado y actualizar contexto/herramientas de la misma tarea antes de continuar con cambios; alternativamente crear una tarea hija explícita vinculada al chat. La UI, almacenamiento y modelo deben coincidir sobre dónde se trabaja.
- P1: normalizar un contrato de motor que reciba contexto, cancelación, herramientas y resultados. Local/Pi/Hermes son adaptadores alternativos por ejecución; no acumular bucles. Cambiar a Pi podría mejorar compactación o ejecución, pero no arregla datos ausentes que Skynet no le pasa.
- La arquitectura no es inviable; el problema principal es la semántica inconsistente del producto y el crecimiento por requisitos sucesivos. No usar LOC como prueba de mala arquitectura: UI y gestión de motores explican parte del crecimiento. Sí revisar responsabilidades de internas/Runtime/Coordinator y duplicaciones chat/tarea/sesión.

### Gaps
- No medí tiempos de arranque de MCP ni una comparación real con Pi en esta auditoría.
- Auditoría de historial de sesiones, recuperación tras Detener y fecha/hora actual está asignada a otro investigador: no duplico aquí ni atribuyo toda la pérdida a compactación.

## ¿El cierre y la verificación distinguen resultado real de apariencia de progreso?

### Takeaway
El verificador separado del modelo es una fortaleza, pero `exit 0` solo demuestra lo que pruebe el comando. Los proyectos nuevos arrancan con una prueba vacía, y Coder puede acabar en HECHA sin una verificación ejecutada. La conversación muestra una inferencia inválida a partir de una captura negra; tampoco demuestra que el juego esté roto ni que sea jugable.

### Cited Findings
- `run_verifier` acepta código cero como éxito. La configuración la escribe el dueño, pero si el comando ejecuta tests dentro del repo el modelo normalmente puede editar esos tests. El prompt de reparación prohíbe debilitarlos; no es una garantía técnica. [Verifier](C:/Git/Skynet/skynet/verifier.py:1), [Coordinator reparación](C:/Git/Skynet/skynet/coordinator.py:234).
- Plantilla nueva: `tests/test_inicio.py` contiene únicamente `assert True`, con nombre `test_el_proyecto_arranca`, y se registra `python -m pytest -q`. Puede devolver verde sin arrancar ninguna aplicación. [Internas](C:/Git/Skynet/skynet/internas.py:79).
- En Coder normal la verificación exige salida completada y archivos tocados o git sucio. El cierre acaba en HECHA si no hay error/límite/verificador fallido; no exige `out.claims_done` ni que exista verificador. HECHA mezcla turno finalizado y objetivo comprobado. [Coordinator](C:/Git/Skynet/skynet/coordinator.py:209), [estado final](C:/Git/Skynet/skynet/coordinator.py:246).
- Tareas largas exigen `strict and out.claims_done` (marcador del modelo) y mínimo de tiempo si se pidió; aceptan iteraciones aunque el verificador falle si cuentas de tests no empeoran. Sin verificador, `strict` es simplemente respuesta completada, pese al comentario posterior que afirma HECHA exige verificador verde. [Scheduler](C:/Git/Skynet/skynet/scheduler.py:170), [cierre](C:/Git/Skynet/skynet/scheduler.py:189), [comentario](C:/Git/Skynet/skynet/scheduler.py:246), [not_worse_than](C:/Git/Skynet/skynet/verifier.py:48).
- La conversación informa 8 tests, incluyendo la corrección de una búsqueda de substring de framework, y después dos capturas negras. Afirma "hay un error JS" sin obtener consola ni un error de ejecución. Eso solo permite concluir "no pude confirmar el resultado visible". [Conversación](C:/Users/HACHO/.codex/attachments/5ea744bd-ef0d-493c-94b8-111c447a244e/Texto%20pegado.txt).
- `vision.capturar_pantalla` selecciona ventana activa por defecto, con opción de título, y devuelve solo imagen; no devuelve título/PID/URL/nombre del proceso ni una validación de que sea el navegador recién abierto. Rechaza ventanas minimizadas, pero no identifica capturas negras como fallo del mecanismo. [Vision](C:/Git/Skynet/skynet_tools/vision.py:65).
- Hay una mejora concreta ya implementada: `navegador.comprobar_html` captura eventos `pageerror` y consola error, hace hasta 8 clics/inputs, lista controles/canvas, detecta overflow y puede devolver imagen. No verifica conservación económica, IA de agentes, Gini, estabilidad prolongada ni efectos semánticos de los controles. Se añade por regex de objetivo solo cuando existe repo en la tarea. [navegador](C:/Git/Skynet/skynet_tools/navegador.cjs:34), [MCP](C:/Git/Skynet/skynet_tools/navegador.py:24), [Runtime](C:/Git/Skynet/skynet/runtime.py:153).
- Tests de navegador validan ejecución real, interacción simple, JS roto, overflow y transmisión de imagen; son mejores que comprobar texto estático. La fixture los omite si no encuentra Playwright en una ruta de runtime Codex. No cubren el simulador completo. [tests navegador](C:/Git/Skynet/tests/test_navegador.py:26).
- El ensayo Colonia Atlas terminó con 120 casos independientes y capturas verificadas, pero PROGRESO reconoce "Codex reparó Skynet y mantuvo el verificador externo". Es evidencia de que el modelo puede construir algo complejo con el harness reparado y un criterio externo fuerte; no es todavía evidencia de autonomía sin asistencia. [PROGRESO](C:/Git/Skynet/PROGRESO.md:49).
- Scheduler hace checkpoint `git add -A`/commit del estado previo, acepta o revierte iteraciones usando `reset --hard` y `clean -fd`; no aparece exclusión por repo en lanzamiento ni en el runner. Cambios ajenos existentes se guardan en commit inicial, pero cambios simultáneos posteriores pueden ser incluidos o descartados. [Scheduler](C:/Git/Skynet/skynet/scheduler.py:118), [lanzamiento](C:/Git/Skynet/skynet/scheduler.py:304), [Gitops](C:/Git/Skynet/skynet/gitops.py:69).

### Inferences
- P0: distinguir estados "respuesta completada", "trabajo guardado sin comprobar", "comprobado" y "objetivo aceptado". Nunca etiquetar un test vacío como arranque de aplicación.
- P1: criterios por tipo de tarea, con pruebas ejecutables: para este simulador, JS ejecutado y 1000+ pasos con semillas, números finitos, saldo/inventario no negativos según reglas, conservación en intercambio, libro de órdenes sin sobreventa, cálculo Gini casos conocidos, población cero, eventos, pausa/reset, memoria acotada y tamaños 390/768/1440. Tests del modelo ayudan, pero aceptación independiente protege contra autoengaño.
- P1: conservar informe con evidencia del objetivo y pruebas, no solo salida final. Una captura negra necesita diagnóstico del capturador/ventana y consola, evitando convertir ausencia de imagen en certeza de error JS.
- P0/P1 seguridad de archivos: permitir un escritor por repo o usar worktrees/snapshots aislados. No desplegar rollback duro en un directorio donde trabaja el usuario a la vez. Esto requiere diseño aprobado, no parche improvisado.
- La política actual de Control total usa regex de riesgo y lista de rutas, no aislamiento del proceso shell. Incluso en Solo repo, un comando permitido puede ejecutar código Python del repo que acceda fuera. Definir si es protección de errores accidentales o una barrera frente a código malicioso; no prometer sandbox completo. La propia integración Hermes ya documenta una política distinta y debe mostrarse claramente.

### Gaps
- No he abierto ni ejecutado el `ecosistema-simulador` del usuario; no sé qué contenían sus ocho tests, si había un error JS real o si la captura falló. El contenido del transcript está abreviado.
- No he intentado explotar shell, ni modificado Git, proyectos personales o agente-godot. Los riesgos de concurrencia se infieren de implementación, no de pérdida observada.

## ¿Es viable el objetivo local y qué demuestran las pruebas actuales?

### Takeaway
Un modelo local más lento y menos capaz puede ofrecer una experiencia fiable si el harness conserva contexto y exige evidencia de éxito. La ventana de 64K no equivale a memoria de sesiones ni garantiza razonamiento: la prueba pegada no demuestra falta de VRAM. Cambiar de harness necesita comparación de resultados sin intervención, no solo tokens/s o una tarea supervisada.

### Cited Findings
- Config actual: Qwen3.8-27B IQ3_S, MTP, contexto 65.536, caché q4 y visión CPU; salida 8192, contexto inicial 6000 y salida de herramienta limitada a 6000 caracteres. El modelo recibe una selección de datos, no todo lo almacenado. [config general](C:/Git/Skynet/config/skynet.toml:7), [modelo](C:/Git/Skynet/config/skynet.toml:47), [Router config](C:/Git/Skynet/config/router.toml:15).
- Ventana estima tokens por caracteres (3,5), reduce resultados antiguos a primera línea y después sustituye grupos por resumen de primeras/últimas acciones. La salida solicitada tiene mínimo 1024 incluso si la estimación de espacio libre es menor; si system/mensaje inicial ya son demasiado grandes no existe un rechazo explícito aquí. Esto es una aproximación útil, no garantía matemática de caber ni resumen semántico completo. [Ventana](C:/Git/Skynet/skynet/ventana.py:22), [max_tokens](C:/Git/Skynet/skynet/ventana.py:118), [ajustar](C:/Git/Skynet/skynet/ventana.py:123).
- El diagnóstico previo del simulador de tareas 169–171 halló salida 8192 truncada, no agotamiento de contexto; D23 corrige lotes truncados/JSON inválido, instrucciones de ediciones pequeñas y continuación acotada. No extrapolar ese diagnóstico a la conversación nueva sin revisar sus eventos. [PROGRESO](C:/Git/Skynet/PROGRESO.md:67), [D23](C:/Git/Skynet/docs/DECISIONES.md:354), [Agent](C:/Git/Skynet/skynet/agent.py:209).
- Bench interno compara Skynet/Hermes con mismo modelo, tests ocultos y una ejecución por tarea; reconoce muestra pequeña y memoria renovada por tarea. Tras D20 ambos resuelven el caso de preferencia entre sesiones. Es evidencia útil de competencia en tareas cerradas, insuficiente para afirmar equivalencia general con Hermes/Claude/Codex. [Comparativa](C:/Git/Skynet/docs/COMPARATIVA-HERMES.md:7), [memoria posterior](C:/Git/Skynet/docs/COMPARATIVA-HERMES.md:79).
- PROGRESO informa pruebas 220/1 omitido, y 185/1 anteriormente; esos son resultados previos del proyecto. El árbol actual tiene además Pi sin commit y bastantes cambios preexistentes; no tratarlos como validación fresca del estado de hoy. [PROGRESO](C:/Git/Skynet/PROGRESO.md:29), [Pi tests](C:/Git/Skynet/tests/test_pi.py:1).
- Tests de memoria cubren guardar/reemplazar/quitar, límites, secretos y que una siguiente sesión reciba la preferencia con LLM guionizado. No validan que un modelo real recuerde tarea cortada después de muchas herramientas, resuelva referencias "esta sesión" o detecte repo seleccionado con Coder apagado. [memoria tests](C:/Git/Skynet/tests/test_memoria.py:1), [ScriptedLLM](C:/Git/Skynet/tests/conftest.py:45).
- Comprobaciones ejecutadas en esta auditoría (11 octubre 2026): `python -m pytest -q` produjo numerosos errores de setup y no completó; se interrumpió mi ejecución. Un test aislado confirmó `OSError could not create numbered dir ... sandbox...AC/Temp/pytest-of-HACHO`. - `skynet.exe doctor` se lanzó y quedó sin reporte tras varios minutos; se interrumpió mi proceso. Solo emitió aviso de ubicación del Python base. Doctor acumula todos los resultados y los imprime al terminar, y prueba MCP para cada repo existente. No diagnostico fallo del modelo ni instalación a partir de ese bloqueo aquí. [doctor](C:/Git/Skynet/skynet/cli.py:204), [cmd_doctor](C:/Git/Skynet/skynet/cli.py:223).

### Inferences
- Prioridad práctica: contrato de contexto/selección y persistencia > verificación y recuperación > simplificación de motores > optimización de velocidad/VRAM. Aumentar 64K no recupera datos que nunca entraron.
- Benchmark de aceptación debe incluir crear repo y seguir en él; generar app y preguntar "en qué quedó"; Detener a mitad de tools; cambiar de sesión y regresar; cambiar de motor; compactar; cerrar/reabrir; fecha/hora/ficheros contradictorios; verificación realmente fallida. Medir éxito sin intervención, correcciones humanas, tiempo total y falsa afirmación de éxito.
- Decisiones caras: identidad sesión–tarea–proyecto y esquema SQLite; contrato común de motores/MCP; política de permisos de subprocess y Hermes; aislamiento/Git rollback; significado verificable de HECHA. Requieren propuesta y OK de Daniel antes de implementar algo grande.
- No recomendar una reescritura ni descartar el modelo con esta evidencia. Un harness pequeño puede fallar si el contrato no coincide con la UI; uno maduro tampoco solucionará el contexto que su envoltorio omite.

### Gaps
- No prueba fresca completa bajo permisos normales: falta suite y doctor terminados en entorno capaz de lanzar MCP. Resultados parciales no certifican rendimiento ni autonomia real.
- No repetí pruebas de memoria real, comparativas con otros harnesses ni mediciones GPU. La investigación externa la realiza el otro agente.
